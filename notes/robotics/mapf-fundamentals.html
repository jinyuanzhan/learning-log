PART A

问题

先把问题本身说清楚：输入是什么、什么叫撞、什么叫好、为什么难。设计题的前五分钟讲的就是这一部分。

02MAPF 是什么

MAPF 是 Multi-Agent Path Finding 的缩写：给很多 robot 同时规划 path，保证它们互相不撞。下文里 agent 就是 robot。

输入

  • 一张 graph G = (V, E)。仓库里通常是 4-connected grid：每个 cell 是一个 vertex，上下左右相邻的 cell 之间有一条 edge。
  • k 个 agent。第 i 个 agent 有一个 start si 和一个 goal gi。

规则

  • 时间是离散的：t = 0, 1, 2, …
  • 每一步，每个 agent 只能做两件事之一：move 到相邻的 cell，或者 wait 在原地。两种 action 都花 1 个 timestep。
  • agent 到达 goal 之后一直停在那里，并且继续占着那个 cell。

输出

每个 agent 一条 path。和单 robot 的 A* 不同，这里的 path 是一张时刻表：path[t] 是它在时刻 t 所在的 cell。

A 的 path:  (1,0)  (1,0)  (1,1)  (1,2)      # t=0 在 (1,0)，t=1 原地 wait，t=2 到 (1,1)，t=3 到 goal
B 的 path:  (0,1)  (1,1)  (2,1)             # t=2 到 goal，之后一直停在 (2,1)

一组 path 是合法的 solution，条件是任意两条 path 之间都没有 conflict。conflict 的定义在下一节。

和单 robot 规划最大的区别同一个 cell 可以被两个 agent 在不同时刻使用。所以问题不再是“这个 cell 能不能走”，而是“这个 cell 在这个时刻能不能走”。后面所有算法都围绕这一点。

03Conflict 的类型

名字定义记法标准 MAPF 里
vertex conflict同一时刻，两个 agent 在同一个 cell⟨ai, aj, v, t⟩禁止
edge conflict，也叫 swap conflict从 t 到 t+1，两个 agent 互换位置⟨ai, aj, u, v, t⟩禁止
following conflict一个 agent 进入另一个 agent 刚离开的 cell允许。真实 robot 要留安全距离，常常禁止
cycle conflict一圈 agent 同时各往前挪一格允许。真实 robot 常常禁止

只检查 vertex conflict 是不够的。两个 agent 对穿时，每个时刻它们都在不同的 cell 里，但物理上已经撞了，所以 edge conflict 要单独检查。

红色的 cell 是发生 conflict 的位置。先看 edge conflict：拖动时间轴，确认每个时刻两个 agent 都不在同一个 cell 里。

面试时先说出假设“Let me state my assumptions: a 4-connected grid, unit time steps, agents can wait, and I only consider vertex and edge conflicts. In a real system I’d also add a following constraint or a safety margin.” 这句话本身就是在澄清问题。

04目标函数

合法的 solution 有很多，需要一个标准来比较好坏。先定义单个 agent 的 cost：它到达 goal 并且不再离开的时刻。中间的 wait 也算在里面。

名字定义什么时候用
SoC（sum of costs，也叫 flowtime）所有 agent 的 cost 之和one-shot MAPF 里最常用
makespan所有 agent 的 cost 里最大的那个关心最后一个 agent 什么时候到
throughput单位时间完成的 task 数lifelong 场景。仓库最关心这个

02 节的例子里，A 的 cost 是 3，B 的 cost 是 2，所以 SoC = 5，makespan = 3。

衡量 planner 本身还有两个指标：planning time（规划一次要多久）和 success rate（限时内找到解的比例）。

One-shot 和 lifelong

  • one-shot MAPF：每个 agent 只有一个 goal，全部到达就结束。02 到 10 节讲的都是它。
  • lifelong MAPF：agent 到达 goal 之后马上拿到新的 goal，永远不结束。仓库属于这一种。

lifelong 的做法是在 one-shot 算法外面套一层“每隔几步 replan”的框架（见 12 节），所以先把 one-shot 学扎实。

05为什么难：joint state space

最直接的想法是把 k 个 agent 看成一个“大 agent”，state 是所有 agent 的位置 (v1, …, vk)，然后直接跑 A*。这样做是 complete 而且 optimal 的，但规模撑不住：

  • state 数是 |V|k。20×20 的 grid 有 400 个 cell，10 个 agent 就是 40010 ≈ 1026 个 state。
  • branching factor 是 5k。每个 agent 有 5 个 action（4 个方向加 wait），10 个 agent 每 expand 一次要生成 510 ≈ 980 万个 successor。

求 SoC 或 makespan optimal 的 MAPF 是 NP-hard 的。所以实用算法都在想办法回避 joint state space，区别只在回避的方式：

做法怎么回避 joint state spacecompleteoptimal大致规模
joint-space A*不回避，所有 agent 一起搜是是几个 agent
CBS各自规划，只在出现 conflict 的地方耦合是是几十个 agent
Prioritized Planning排好顺序一个一个规划，后面的让前面的否否上百到上千个 agent

从上到下，耦合越来越松，速度越来越快，保证越来越少。这条从 coupled 到 decoupled 的轴，是整个领域最基本的 tradeoff。

面试怎么说“The difficulty of MAPF is that the joint state space grows exponentially with the number of agents: |V|k states and a branching factor of 5k. So instead of searching the joint space, I’d plan each agent separately and then resolve the conflicts.”

06A* 回顾：可能被追问的理论

A* 你已经会写了，这一节只列容易被追问的点。

被问 “Are you familiar with A*?”“Yes. A* is a shortest-path search on a graph, for example a grid map. It’s best-first search: it always expands the node with the smallest f, where f is g, the cost from the start so far, plus h, a heuristic estimate of the remaining cost to the goal. The heuristic is what makes it faster than Dijkstra, because it pulls the search toward the goal instead of spreading out in every direction. As long as the heuristic is admissible, meaning it never overestimates, the path it returns is optimal. On a 4-connected grid the usual heuristic is Manhattan distance, and in MAPF people often precompute the true distance to each goal with a backward BFS.”

f(n) = g(n) + h(n) g(n)：从 start 到 n 已经花掉的 cost h(n)：从 n 到 goal 还要花多少的估计，也就是 heuristic 每次从 OPEN 里 pop 出 f 最小的 node

Admissible 和 consistent

  • admissible：h(n) 永远不高估真实的剩余 cost。满足它，A* 返回的 path 就是 optimal 的。
  • consistent：对每条 edge (n, n′) 都有 h(n) ≤ c(n, n′) + h(n′)，并且 h(goal) = 0。直观上就是 heuristic 满足三角不等式。满足它，f 沿着任何 path 都不会下降，每个 node 只需要 expand 一次。
  • consistent 的 heuristic 一定 admissible，反过来不一定。只 admissible 不 consistent 时，已经进了 CLOSED 的 node 可能要 reopen，否则结果可能不是 optimal。

Grid 上用什么 heuristic

  • Manhattan distance：在 4-connected grid 上是 consistent 的。但它看不见障碍物，障碍物多的时候估得太低，A* 会 expand 很多没用的 node。
  • true-distance heuristic：从 goal 出发做一次反向 BFS（edge 有权重时用反向 Dijkstra），得到每个 cell 到 goal 的真实最短距离，存成一张表，之后查表是 O(1)。MAPF 里基本都这么做：每个 goal 预计算一次，后面成百上千次搜索都复用这张表。

几个常见追问

问题答案
f 相同的 node 先 pop 哪个？先 pop g 大的。g 大说明离 goal 更近，能少 expand 很多 node。这叫 tie-breaking。
怎么让 A* 更快？更准的 heuristic，好的 tie-breaking，或者用 weighted A* 牺牲一点 optimality。
weighted A* 是什么？f = g + w·h，其中 w > 1。搜索更贪心、更快，返回的 path cost 不超过 optimal 的 w 倍。这种有上界的次优叫 bounded-suboptimal。
A* 和 Dijkstra、BFS 的关系？h = 0 的 A* 就是 Dijkstra。edge cost 全是 1 的 Dijkstra 就是 BFS。

07Space-time A*

先解决最小的多 agent 问题：别的 agent 的 path 已经定了，给我这一个规划一条不撞它们的 path。后面的 Prioritized Planning 和 CBS，底层都是反复调用这一步。

被问 “Are you familiar with space-time A*?”“Space-time A* is A* extended to multi-robot settings. The state is a cell plus a time step, and besides moving to a neighbor, the robot can also wait in place. The paths of other robots go into a reservation table, so the search just skips any cell-and-time, or any edge, that’s already taken. That lets one robot plan around robots whose paths are already fixed. It’s the building block of both prioritized planning and CBS. One subtle point is the goal test: reaching the goal only counts if no other robot needs to pass through that cell later.”

思路：把时间加进 state

普通 A* 的 state 是位置 v。多 agent 时，一个 cell 现在被占，不代表两步之后还被占，所以 state 要变成 (v, t)：在时刻 t 位于 v。

普通 A*space-time A*
statev(v, t)
actionmove 到相邻的 cellmove 到相邻的 cell，或者 wait。两者都让 t 加 1
障碍物静态的墙墙，加上 reservation table 里别人占用的时空位置
heuristic到 goal 的距离不变，还是到 goal 的空间距离
goal 条件v == goalv == goal，并且之后没有人再预约 goal

Reservation table

一张 hash table，记录别的 agent 已经占用的时空位置，查询是 O(1)。它存三种东西，正好对应 03 节的 conflict：

  • vertex reservation (v, t)：时刻 t，cell v 有人。用来防 vertex conflict。
  • edge reservation (u→v, t)：别人在 t 到 t+1 从 v 走到 u，所以我不能同时从 u 走到 v。用来防 edge conflict。
  • 停在 goal 的 agent：从它到达的时刻起，goal 那个 cell 永久被占。

Pseudo-code

function SpaceTimeAStar(start, goal, RT, T_max):
    OPEN ← priority queue，按 f = g + h 排序
    push (start, t=0)，g = 0
    CLOSED ← {}
    while OPEN 非空:
        (v, t) ← pop f 最小的
        if (v, t) in CLOSED: continue
        CLOSED.add((v, t))
        if v == goal and RT 里 goal 在 t 之后没有 reservation:
            return 沿 parent 指针回溯出的 path
        if t ≥ T_max: continue
        for u in neighbors(v) ∪ {v}:              # {v} 就是 wait
            if (u, t+1) in RT.vertex: continue    # vertex conflict
            if (v→u, t) in RT.edge:   continue    # edge conflict
            push (u, t+1)，g = t+1，f = g + h(u)
    return FAIL

三个容易漏的细节

  1. goal 条件。agent 到达 goal 之后会停在那里。如果之后某个时刻别人要经过这个 cell，现在就不能算完成，要继续搜。实验台的第三个场景演示的就是这一点。
  2. T_max。问题无解时，wait 可以无限重复，搜索不会自己停。可以取 T_max = 最后一个 reservation 的时刻 + free cell 的个数。理由是：过了最后一个 reservation，环境就是静态的了，而静态环境里的最短路不会超过 free cell 的个数。
  3. heuristic 为什么还 admissible。加了时间只会让实际 cost 变大，多出来的是 wait 和绕路。空间上的最短距离仍然不会高估。

复杂度：state 最多有 |V| × T_max 个，每个 state 有 5 个 successor。

橙色的 B 的 path 已经定了，蓝色的 A 是 space-time A* 当场规划出来的。前两个场景都试一次关掉 wait，看 A 的结果怎么变。第三个场景看 A 到了 goal 之后为什么还要让开。

可以直接运行的 Python：space-time A* 和 Prioritized Planning
import heapq

def space_time_astar(grid, start, goal, reserved_v, reserved_e, parked, t_max):
    """grid[r][c] == '#' 是墙，cell 写成 (r, c)。
    reserved_v: {(cell, t)}        时刻 t 这个 cell 被占
    reserved_e: {(u, v, t)}        t→t+1 不能从 u 走到 v
    parked:     {cell: t0}         从 t0 起这个 cell 永久被占（别的车停在 goal 上）"""
    H, W = len(grid), len(grid[0])
    h = lambda c: abs(c[0] - goal[0]) + abs(c[1] - goal[1])        # Manhattan distance
    # goal 最晚被别人预约到什么时候：在那之前到达不算完成
    goal_free_from = max((t + 1 for (c, t) in reserved_v if c == goal), default=0)

    open_list = [(h(start), 0, start)]      # (f, -g, cell)。unit cost 下 g 就是 t；用 -g 让 f 相同时先 pop g 大的
    parent = {(start, 0): None}
    closed = set()
    while open_list:
        _, neg_t, cur = heapq.heappop(open_list)
        t = -neg_t
        if (cur, t) in closed:
            continue
        closed.add((cur, t))
        if cur == goal and t >= goal_free_from:                     # 到了 goal，而且之后没人再预约它
            path, node = [], (cur, t)
            while node is not None:
                path.append(node[0])
                node = parent[node]
            return path[::-1]                                       # path[t] 就是时刻 t 的位置
        if t >= t_max:
            continue
        r, c = cur
        for nxt in [(r - 1, c), (r, c + 1), (r + 1, c), (r, c - 1), (r, c)]:   # 最后一个是 wait
            nr, nc = nxt
            if not (0 <= nr < H and 0 <= nc < W) or grid[nr][nc] == '#':
                continue
            if (nxt, t + 1) in reserved_v:                          # vertex conflict
                continue
            if nxt in parked and t + 1 >= parked[nxt]:              # 别人已经停在那里
                continue
            if (cur, nxt, t) in reserved_e:                         # edge (swap) conflict
                continue
            if (nxt, t + 1) not in parent:
                parent[(nxt, t + 1)] = (cur, t)
                heapq.heappush(open_list, (t + 1 + h(nxt), -(t + 1), nxt))
    return None


def prioritized_planning(grid, starts, goals, order):
    reserved_v, reserved_e, parked, paths = set(), set(), {}, {}
    free_cells = sum(row.count('.') for row in grid)
    for i in order:                                                 # priority 从高到低
        t_max = max((t for (_, t) in reserved_v), default=0) + free_cells
        path = space_time_astar(grid, starts[i], goals[i], reserved_v, reserved_e, parked, t_max)
        if path is None:
            return None                                             # 这个顺序失败了
        paths[i] = path
        for t, cell in enumerate(path):
            reserved_v.add((cell, t))
            if t + 1 < len(path) and path[t + 1] != cell:
                reserved_e.add((path[t + 1], cell, t))              # 禁止别人反向对穿
        parked[path[-1]] = len(path) - 1                            # 到 goal 后永久占用
    return paths


if __name__ == '__main__':
    grid = ['...', '...', '...']                                    # 十字路口
    starts, goals = {'A': (1, 0), 'B': (0, 1)}, {'A': (1, 2), 'B': (2, 1)}
    print(prioritized_planning(grid, starts, goals, ['B', 'A']))

PART C

多个 agent

两种最基础的做法：排好顺序一个一个规划，或者一起规划、有 conflict 再解决。其他算法几乎都是这两种的变体。

08Prioritized Planning

有了 space-time A*，多 agent 规划最简单的办法就出来了：排一个 priority 顺序，按顺序一个一个规划，后面的把前面所有 agent 的 path 当成 reservation。这就是 Prioritized Planning，简称 PP，也叫 Cooperative A*。

被问 “Are you familiar with prioritized planning?”“Prioritized planning is the simplest practical approach to multi-agent path finding. You give the robots a priority order and plan them one at a time with space-time A*. Each robot treats the paths of all higher-priority robots as moving obstacles. It’s fast, just one single-agent search per robot, so it scales to hundreds or even thousands of robots. The downside is that it’s neither complete nor optimal: a bad order can make it fail even when a solution exists. So choosing the order matters a lot, for example by deadline, and when it fails you can retry with a different order.”

function PrioritizedPlanning(agents, order):
    RT ← 空的 reservation table
    for i in order:                               # priority 从高到低
        path_i ← SpaceTimeAStar(s_i, g_i, RT, T_max)
        if path_i == FAIL: return FAIL            # 或者换一个顺序重试
        把 path_i 的每个 (cell, 时刻) 和每条 edge 写进 RT
        把 g_i 从到达时刻起永久写进 RT            # 停在 goal 上
    return 所有 path

一共只调用 k 次单 agent 搜索，所以很快，能用到上百上千个 agent。代价是 complete 和 optimal 两个保证都没有了。

每个场景都把所有 priority 顺序点一遍。重点看三个：终点挡路里顺序改变 cost，走廊 + 居中避让位里两种顺序都失败，3 个 agent 里六种顺序都成功但都不是 optimal。

为什么不 complete

complete 的意思是：问题有解时一定能找到。PP 做不到。高 priority 的 agent 规划时完全不知道后面还有谁，只管走自己的最短路，而且 path 一旦定下就不再改。

看“走廊 + 居中避让位”：A 先规划，径直穿过走廊，B 就没有任何合法的 path 了。B 先规划也一样。但这个问题是有解的，其中一个先进避让位等一下就行。切到 CBS 实验台的同一个场景可以看到这个解。

为什么不 optimal

  • “终点挡路”：B 先规划，就早早停在了 A 的必经之路上，A 只能绕路，SoC 是 6。A 先规划，SoC 是 4。
  • “3 个 agent”：六种顺序的 SoC 是 9 或 10，而 optimal 是 7。原因是排在前面的 agent 在几条一样短的 path 里随便选了一条，恰好挡住了后面的 agent。它不知道后面还有谁，所以没法选对。

Priority 怎么定

规则理由
deadline 近的优先最自然的业务规则。Symbotic 的公开 blog 写的就是这个：每个 case 有出库的 deadline，最紧急的 case 决定哪些 robot 优先
剩余距离长的优先path 长的 agent 更难绕路
要离开 corridor 的，优先于要进去的先把窄的地方腾空，防止堵死
失败后换一个顺序重试便宜而有效的 baseline

失败了怎么办

  • 换顺序重试，通常是把失败的那个 agent 提到前面。
  • 让失败的 agent 这一轮先原地 wait，或者退到最近的空位，下一轮 replan 时再规划。
  • 只对卡住的这几个 agent 用 CBS 做一次小规模求解。

什么时候保证能成功

直观的条件是：停车位不在主干道上。准确的说法叫 well-formed：任意两个 endpoint（某个 agent 的 start 或 goal）之间，都存在一条不经过其他 endpoint 的 path。在这样的地图上，只要再加一条规则“高 priority 的 agent 不穿过别人的 start”，PP 就保证成功。因为低 priority 的 agent 最坏可以在自己的 start 等所有人停好，再走一条不经过任何 endpoint 的 path。仓库设计时会尽量满足这一点，比如取货位在货架旁边，不占主通道。

面试怎么说“As a baseline I’d use prioritized planning: order the robots by priority and plan them one by one with space-time A*, treating earlier paths as moving obstacles. It scales almost linearly, but it’s neither complete nor optimal, because a high-priority robot can park on a low-priority robot’s only route. I’d mitigate that with deadline-based priorities, retrying with a different order, and a local CBS repair.”

09CBS：Conflict-Based Search

PP 的毛病在于顺序一开始就定死了。CBS 换了一个思路：先让每个 agent 各走各的最短路，完全不管别人。发现 conflict 之后，再用 constraint 一点一点把 conflict 消掉。

被问 “Are you familiar with CBS?”“Yes. CBS, conflict-based search, is a classic optimal algorithm for multi-agent path finding, and it has two levels. At the low level, each robot plans its own shortest path, ignoring the others. At the high level, CBS checks those paths for conflicts, like two robots in the same cell at the same time, or two robots swapping cells. When it finds one, it branches into two children: in one, robot A gets a constraint to stay out of that cell at that time; in the other, robot B does. Only that one robot replans. The high level searches this constraint tree best-first by total cost, so the first conflict-free solution it finds is optimal. It works well when conflicts are sparse, but it can grow exponentially in dense areas like narrow corridors.”

核心观察

假设 A 和 B 在时刻 t 都在 cell v，也就是有一个 vertex conflict ⟨A, B, v, t⟩。那么在任何合法的 solution 里，下面两件事至少有一件成立：

  • A 在时刻 t 不在 v。
  • B 在时刻 t 不在 v。

CBS 不去猜是哪一种，而是分成两支，两种都试。每一支给一个 agent 加一条 constraint，并且只让这一个 agent 重新规划。

两层结构

搜索什么怎么搜
high levelconstraint tree，简称 CT。每个 node 存三样东西：一组 constraint、满足这些 constraint 的一组 path、这组 path 的 SoCbest-first：每次 pop cost 最小的 node
low level单个 agent 的 path，要满足这个 agent 身上的所有 constraint07 节的 space-time A*，把 reservation table 换成这个 agent 自己的 constraint

constraint 有两种，和 conflict 一一对应：

  • vertex constraint ⟨a, v, t⟩：agent a 在时刻 t 不能在 v。
  • edge constraint ⟨a, u, v, t⟩：agent a 不能在 t 到 t+1 从 u 走到 v。

Pseudo-code

function CBS(agents):
    Root.constraints ← {}
    Root.paths ← 每个 agent 各自的最短路              # low level，互相不管
    Root.cost ← SoC(Root.paths)
    OPEN ← {Root}
    while OPEN 非空:
        N ← pop cost 最小的 node
        C ← N.paths 里的第一个 conflict
        if C 不存在: return N.paths                   # 没有 conflict，这就是 optimal 解
        for a in C 涉及的两个 agent:
            M ← N 的拷贝
            M.constraints ← N.constraints + {a 不能出现在 C 的位置和时刻}
            M.paths[a] ← LowLevel(a, M.constraints)   # 只有 a 重新规划
            if M.paths[a] 存在:
                M.cost ← SoC(M.paths)
                push M
    return FAIL

手推：十字路口

3×3 的 grid。A 从 (1,0) 到 (1,2)，从左往右。B 从 (0,1) 到 (2,1)，从上往下。两条最短路在正中间的 (1,1) 交叉。

  1. Root。没有 constraint。A 走 (1,0) (1,1) (1,2)，cost 2。B 走 (0,1) (1,1) (2,1)，cost 2。SoC = 4。检查 conflict：t=1 时两个都在 (1,1)。
  2. 分两支。N1 给 A 加 constraint：A 在 t=1 不能在 (1,1)。A 重新规划，先 wait 一步再走，cost 3，B 不变，SoC = 5。N2 对称，给 B 加 constraint，SoC 也是 5。
  3. 继续。OPEN 里是 N1 和 N2，cost 都是 5。pop N1，检查 conflict，没有。返回 N1 的 path，optimal SoC = 5。

A 也可以绕路，但绕路的 cost 是 4，比 wait 一步的 3 大，所以 low level 选了 wait。

先在十字路口点两次“下一步”，和上面的手推对一遍。再到两个房间 + 长走廊点“跑到结束”，看只有 2 个 agent 的时候 CT 能长到多大。

为什么是 optimal 的

  1. 分支不会丢掉解。任何合法的 solution，在那个 conflict 上要么 A 让了，要么 B 让了，所以它一定满足两个子 node 里至少一个的 constraint。
  2. node 的 cost 是一个 lower bound。node 里每个 agent 走的都是满足 constraint 的最短路，还没处理的 conflict 被忽略了。所以满足这些 constraint 的任何合法 solution，cost 都不会比它小。
  3. best-first 保证先找到的最好。high level 总是 pop cost 最小的 node。第一个被 pop 出来而且没有 conflict 的 node，cost 不大于 OPEN 里所有其他 node 的 lower bound，所以它就是 optimal。

这和 A* 的 optimal 证明是同一个逻辑：按 lower bound 从小到大看，第一个真正可行的就是最好的。

CBS 也是 complete 的，有解就一定能找到。但问题无解时它不会自己停下来，要另外设 node 数上限或者时间上限。

什么时候慢

每个 conflict 让 tree 分一次叉，最坏情况下 node 数是指数级的。看“两个房间 + 长走廊”：只有 2 个 agent，在 one-wide corridor 里对头，其中一个必须等另一个完全通过，SoC 要比 root 多出 5。CBS 每加一条 constraint 只能把 cost 抬高一点，而且每一层都有“A 让”和“B 让”两种选择，于是一共要生成 63 个 node。corridor 每加长一格，node 数翻一倍：

corridor 长度123456
CBS 生成的 node 数153163127255511

这些数字是本页的实现实际跑出来的。同一个场景，PP 一次就得到了 cost 相同的解。

结论：CBS 适合 conflict 稀疏的情况。agent 密、corridor 多的时候会很慢，而仓库正是这样。实际使用时要靠各种加速技巧，或者放弃 optimal 来换速度。

面试怎么说“If I need a quality guarantee I’d use CBS. The high level does best-first search on a constraint tree: when two agents conflict, it branches into two children, each adding a constraint to one of the agents. The low level replans just that agent with space-time A*. It’s optimal for sum of costs, because branching never loses a solution and node costs are lower bounds. The downside is exponential growth when conflicts are dense, for example two robots head-on in a one-wide corridor.”

两者之间还有什么

下面两个知道名字和一句话就够，不用会写。

  • ECBS：允许 solution 的 cost 最多是 optimal 的 w 倍，比如 w = 1.2，换来快几个数量级。做法是在 cost 不超过 w 倍 lower bound 的 node 里，优先 expand conflict 最少的那个。思想和 06 节的 weighted A* 一样，都是 bounded-suboptimal。
  • PBS：和 CBS 一样在 conflict 处分支，但分支的内容是“A 的 priority 高于 B”还是反过来，然后按这个顺序跑 PP。相当于自动搜索 PP 的 priority 顺序。

被问 “Are you familiar with ECBS?”只要求知道思路的算法，开头先说清楚没有实现过，比硬撑更好。“I know the idea, though I haven’t implemented it. ECBS is a bounded-suboptimal version of CBS. You choose a factor, say 1.2, and it guarantees the solution cost is at most 1.2 times the optimal. In exchange it’s much faster, because among the nodes within that bound it expands the ones with the fewest conflicts first. It’s the same idea as weighted A*: trade a bounded amount of quality for a lot of speed.”

被问 “Are you familiar with PBS?”只要求知道思路的算法，开头先说清楚没有实现过，比硬撑更好。“I know the idea, though I haven’t implemented it. PBS, priority-based search, combines CBS and prioritized planning. When two robots conflict, instead of adding a location constraint, it branches on which of the two gets higher priority, and then replans with that ordering. So it’s essentially searching for a good priority order for prioritized planning. It isn’t guaranteed to be optimal, but it’s fast and works well when the map is crowded.”

系统设计

11从算法到系统

真实仓库比 one-shot MAPF 多三个问题：goal 从哪来，task 不停地来怎么办，robot 没按计划走怎么办。一个调度系统通常分成三层，靠一个定时循环连起来。

12Lifelong MAPF 与 rolling horizon

仓库里 robot 到达 goal 之后马上有新的 task，问题永远不结束，目标是 throughput。两种朴素做法都不行：

  • 每次有 robot 到达，就给所有 robot 完整地重新解一次 MAPF：太慢。而且很远的 conflict 现在解了也白解，因为到那时 goal 早就变了。
  • 只给拿到新 task 的 robot 规划，其他 robot 的 path 不动：越到后面越挤，容易堵死。

Rolling horizon

折中的办法是定时 replan，但每次只管眼前的一段。有两个参数：

  • planning window w：只保证未来 w 步内没有 conflict。path 仍然规划到 goal，但 w 步之后的 conflict 不检查。
  • replanning period h：每执行 h 步，重新规划一次。要求 h ≤ w，这样真正执行掉的那 h 步都在已经消除 conflict 的范围里。

被问 “Are you familiar with rolling-horizon planning?”“Rolling-horizon planning is how you handle lifelong MAPF, where robots keep getting new tasks and the problem never ends. Instead of solving everything once, you replan every h time steps, and each time you only resolve conflicts within the next w steps, with h no larger than w. Robots still plan all the way to their goals, but conflicts beyond the window are ignored, because the situation will have changed by then. The two parameters trade quality against planning time: a short window is fast but short-sighted, a long one is slower. Inside the window you can run any MAPF solver, and windowed prioritized planning is the common choice.”

loop 每 h 个 timestep:
    给已经到达 goal 的 agent 分配新的 goal          # task assignment
    paths ← WindowedMAPF(当前位置, goals, w)        # 只在未来 w 步内消除 conflict
    执行每条 path 的前 h 步

WindowedMAPF 可以是任何 one-shot 算法的 window 版本。最简单的是 windowed PP：在 space-time A* 里，t 超过 w 之后就不再查 reservation table。

w 和 h 怎么选

太小太大
w短视。看不到稍远的 conflict，容易把 robot 带进堵点规划慢。远处的 conflict 解了也白解
hreplan 太频繁，算力开销大对新 task 和延误的反应慢

常见的取法是 w 为 h 的几倍，然后在仿真里扫参数。一篇和 Symbotic 合作的公开论文用的是 w = 20、h = 5。

规划和执行是重叠的

  • 规划需要时间，这段时间里 robot 还在走。所以规划的起点不是现在的位置，而是这一轮规划结束时预计到达的位置。
  • 规划超时怎么办：继续执行上一轮 path 剩下的部分。因为 w 大于 h，上一轮的 path 还有 w − h 步没有 conflict 的余量。

面试怎么说“A warehouse is a lifelong problem, so I’d use a rolling horizon: replan every h steps, and only resolve conflicts within the next w steps, with h ≤ w. A small w is fast but myopic; a large w is slow and wastes effort on conflicts that will change anyway. If planning times out, robots keep following the leftover part of the previous plan.”

13Task assignment

n 个空闲的 robot，m 个待做的 task。把 robot i 派去做 task j 的代价是 cij。每个 robot 最多做一个 task，每个 task 最多给一个 robot，要让总 cost 最小。这叫 linear assignment problem。

被问 “Are you familiar with the Hungarian algorithm?”“Yes. The Hungarian algorithm solves the linear assignment problem: given n robots, n tasks, and a cost for every robot–task pair, it finds the one-to-one matching with the minimum total cost. It’s optimal and runs in O(n³). In a warehouse, the cost could be the travel time to the pickup plus terms for the deadline and congestion. Compared with greedy nearest-robot assignment, which can be far from optimal, it gives the globally best matching. In practice I’d just call a library, like linear_sum_assignment in SciPy.”

Cost matrix 怎么建

c_ij = robot i 到 pickup 的距离 # 用 06 节的 true distance，不用 Manhattan distance + pickup 到 delivery 的距离 + deadline 项 # task 越急，cost 越低 + congestion penalty # 目的地附近已经派去了多少 robot

Greedy 不是 optimal 的

greedy 每次挑 cost 最小的一对。先挑 (R1, T1)，cost 1。剩下只能 (R2, T2)，cost 10。总共 11。而 optimal 是 (R1, T2) 加 (R2, T1)，总共 4。greedy 把最近的 robot 抢走了，别的 task 只能分给很远的 robot。

如果只按距离分配，可能把 10 个 robot 派进同一条 aisle。距离上最优，实际上全在排队。两个办法：在 cost 里加 congestion penalty，或者直接用规划出来的时间代替距离。

面试怎么说“For task assignment I’d build a cost matrix: travel time to the pickup plus pickup-to-drop, with a deadline term and a congestion penalty, and solve it with the Hungarian algorithm, which is optimal in O(n³). Greedy nearest-robot is the fast baseline. The key tradeoff is that solving assignment and routing separately is fast but can send many robots into the same aisle.”

14Corridor 与 deadlock

deadlock 是指一组 robot 互相等对方让开，结果谁都动不了。最典型的是 one-wide corridor 里两个 robot 对头：A 要去的 cell 被 B 占着，B 要去的 cell 被 A 占着。

完整的 space-time 规划本身不会产生 deadlock，因为每一步谁走谁等都排好了。deadlock 出现在两个地方：rolling horizon 的 window 之外没人管；执行时 robot 没按计划走。

检测：wait-for graph

每个 robot 是一个 node。如果 A 下一步要去的 cell 被 B 占着，就画一条 A→B 的 edge，意思是 A 在等 B。图里有环就是 deadlock。找环用 DFS，或者沿着 edge 一路走，看会不会回到出发点。

Symbotic 作者 2026 年 11 月的一篇公开论文里，仓库地图上 691 个 free cell 有 470 个在 one-wide corridor 里，分析出的 bottleneck 正是 corridor 的入口。“出 corridor 的优先”是那篇论文里提到的机制之一。

面试怎么说“I’d handle deadlock mostly by prevention: treat each one-wide aisle as a single resource that’s reserved for one direction at a time, give robots leaving an aisle priority over robots entering, and only admit a robot when its exit is free. As a fallback I’d keep a wait-for graph at execution time, detect cycles, and back out the lowest-priority robot.”

15延误与故障

规划时假设每一步刚好花 1 个 timestep。真实的 robot 会慢，会停。如果所有 robot 都死守时刻表，一个 robot 晚了 1 秒，就可能撞上按时到达的另一个。

只守先后顺序，不守时刻

如果 plan 里 A 先经过 cell v，B 后经过，那么执行时 B 必须等 A 真的离开 v 之后才能进。只要这个先后顺序不变，不管怎么延误都不会撞。论文里把这种依赖关系画成一张图，叫 Action Dependency Graph，简称 ADG。知道这个思路和名字就够。

代价是延误会传染：A 慢了，所有排在 A 后面的 robot 都跟着等。所以要设一个阈值，延误超过它就触发 replan。

Robot 故障

  • 把故障的 robot 当成新的障碍物写进地图。
  • path 经过它的 robot 重新规划，其他 robot 不动。
  • 它身上的 task 重新做 assignment。
  • 如果它堵在 one-wide aisle 里，里面的 robot 只能从另一头出去，或者等人工处理。

面试怎么说“At execution time I wouldn’t enforce exact timestamps, only the ordering: if the plan says A passes a cell before B, then B waits until A has actually left. That keeps the plan collision-free under delays. If the delay grows beyond a threshold, I’d trigger a replan.”

16规模再大怎么办

1000 个以上的 robot，每几秒就要 replan 一次。办法按从简单到复杂排：

  1. window。rolling horizon 已经把每次规划的时间范围砍到了 w 步。
  2. 分区。按楼层或者区域把仓库切开，每块各自规划，可以并行。区域边界上的 cell 用 reservation 来协调。每层 100 多个 robot、层与层之间独立，就是天然的分区。
  3. 只 replan 受影响的。没有新 task、path 也没被别人影响的 robot，沿用旧 path。
  4. anytime。先用最快的方法拿到一个可行解，剩下的时间预算再用来改进质量。
  5. 更快的 solver。知道一个名字就够：PIBT。它不规划整条 path，每个 timestep 只决定所有 robot 的下一格，priority 高的先选，挡路的被推开。上千个 robot 也只要毫秒级，但 path 质量一般。

被问 “Are you familiar with PIBT?”只要求知道思路的算法，开头先说清楚没有实现过，比硬撑更好。“I know the idea, though I haven’t implemented it. PIBT, priority inheritance with backtracking, is a very fast MAPF method for large fleets. Instead of planning full paths, it only decides the next move of every robot at each time step. Robots choose their next cell in priority order, and if a higher-priority robot wants a cell occupied by a lower-priority one, that robot inherits the priority and has to move out of the way; if it gets stuck, it backtracks. It runs in milliseconds even with thousands of robots. The tradeoff is lower path quality than search-based planners like CBS.”

  • assignment：每个新 task 分给最近的空闲 robot，也就是 greedy。
  • planning：Prioritized Planning，deadline 近的优先。每个 robot 跑 space-time A*，reservation table 里记 vertex 和 edge 两种 reservation。
  • 缺陷：PP 不 complete 也不 optimal；one-wide aisle 里容易堵死；greedy 不看拥堵；每次都规划到 goal，1000 个 robot 算不完。

第 4 步：tradeoff

挑两三个讲，每个都说清楚选了什么、放弃了什么。

  • optimal 和实时。CBS 有保证，但撑不住 1000 个 robot。PP 快，但没有保证。所以用 PP 做主干，CBS 只做局部修复。
  • w 的大小。小了短视，大了慢。在仿真里扫参数，看 throughput 和 planning time 的 p99。
  • assignment 和 planning 分开解，还是一起解。分开解快，但可能把 robot 派进堵点。一起解质量好，但慢。先分开解，再用 congestion penalty 弥补。
  • centralized 和 decentralized。centralized 有全局信息，质量好，但有算力瓶颈和单点故障。仓库通常是 centralized 的规划，加上 robot 本地的安全机制。

第 5 步：边界情况

  • one-wide aisle 里对头。
  • 规划超时：沿用上一轮剩下的 path。
  • robot 故障，占着一个 cell 不动。
  • task 突然增多，或者某个区域过度拥堵：限制同时进入这个区域的 robot 数。robot 越多不等于 throughput 越高。
  • priority 低的 robot 一直等，这叫 starvation：让等待时间越长的 robot priority 越高。

第 6 步：指标

  • throughput：每小时完成的 task 数。
  • 准时率：在 deadline 之前完成的 task 比例。
  • planning time 的平均值和 p99。
  • robot 的 wait 时间占比、空驶距离占比。
  • deadlock 的次数。

18面试题与答案

问题定义

MAPF 的输入和输出是什么？

输入是一张 graph 和 k 个 agent 的 start、goal。时间离散，每一步每个 agent 要么 move 到相邻的 cell，要么 wait。输出是每个 agent 一条带时间的 path，任意两条之间没有 vertex conflict 和 edge conflict。目标通常是最小化 SoC 或 makespan，lifelong 场景看 throughput。

为什么只检查 vertex conflict 不够？

两个 agent 对穿时，每个时刻它们都在不同的 cell 里，vertex conflict 检查不出来，但物理上已经撞了。所以要单独检查 edge conflict：t 到 t+1 之间两个 agent 互换了位置。

为什么不直接在 joint state space 上跑 A*？

state 数是 |V|k，branching factor 是 5k，都随 agent 数指数增长。20×20 的 grid 上 10 个 agent 就有大约 1026 个 state，每次 expand 要生成约 980 万个 successor。所以实用算法都是先各自规划，再处理 conflict。

SoC 和 makespan 有什么区别？仓库里看哪个？

SoC 是所有 agent 到达时间的和，makespan 是最晚到达的那个时间。仓库是 lifelong 场景，看的是 throughput。SoC optimal 不等于 throughput optimal，因为 throughput 还取决于 task assignment、拥堵和执行时的延误。

A* 和 space-time A*

admissible 和 consistent 有什么区别？

admissible 是 h 从不高估真实的剩余 cost，它保证 A* 返回 optimal 的 path。consistent 是 h(n) ≤ c(n, n′) + h(n′)，它保证 f 沿 path 不下降，每个 node 只需要 expand 一次。consistent 一定 admissible，反过来不一定。只 admissible 不 consistent 时，CLOSED 里的 node 可能要 reopen。

有障碍物的 grid 上，怎么得到比 Manhattan distance 更准的 heuristic？

从 goal 做一次反向 BFS，edge 有权重时用反向 Dijkstra，得到每个 cell 到 goal 的真实最短距离，存成表。它考虑了障碍物，仍然 admissible 而且 consistent。每个 goal 只算一次，之后所有搜索都复用。

space-time A* 和普通 A* 差在哪？

state 从 v 变成 (v, t)。action 多了一个 wait。障碍物除了墙，还有 reservation table 里别人占用的时空位置，分 vertex 和 edge 两种。goal 条件多了一条：到达之后 goal 不能再被别人预约。heuristic 不变。

agent 一到 goal 就能结束搜索吗？

不能。agent 到达之后会停在 goal 上。如果之后某个时刻别人要经过这个 cell，那么现在停下就会撞。必须检查 goal 在这之后没有任何 reservation，否则继续搜，结果可能是先让开再回来。

加了时间维之后，heuristic 还 admissible 吗？

还是。heuristic 是到 goal 的空间最短距离。加了时间和 reservation 之后，实际的 cost 只会更大，因为多出来的是 wait 和绕路，所以空间距离仍然不会高估。

问题无解时，space-time A* 怎么停下来？

因为有 wait，state 可以无限多，所以要设一个 T_max。可以取最后一个 reservation 的时刻加上 free cell 的个数：过了最后一个 reservation，环境是静态的，最短路不会超过 free cell 的个数。超过 T_max 的 state 不再 expand。

reservation table 用什么数据结构？

hash set。vertex reservation 的 key 是 (cell, t)，edge reservation 的 key 是 (u, v, t)，查询都是 O(1)。停在 goal 上的 agent 另外存一张 cell 到起始时刻的表。配合 rolling horizon 时，只需要存未来 w 步。

Prioritized Planning 和 CBS

PP 为什么不 complete？举一个例子。

高 priority 的 agent 规划时不考虑后面的 agent，path 定了也不再改。例子：one-wide corridor 中间有一个避让位，A 和 B 从两头对穿。不管谁先规划，先规划的都径直穿过去，后规划的没有任何合法的 path。但问题有解，其中一个先进避让位就行。

PP 的 priority 怎么定？

常用的规则：deadline 近的优先；剩余距离长的优先；要离开 corridor 的优先于要进去的；失败之后换一个顺序重试。也可以让等待时间越长的 agent priority 越高，防止 starvation。

PP 失败了怎么办？

三个层次。先换顺序重试，把失败的 agent 提前。还不行，就让失败的 agent 这一轮先 wait，下一轮 replan 时再规划。再不行，对卡住的几个 agent 用 CBS 做局部求解。

CBS 的两层各做什么？

high level 在 constraint tree 上做 best-first search。每个 node 有一组 constraint、一组 path 和它们的 SoC。每次 pop cost 最小的 node，找第一个 conflict，分成两个子 node，每个子 node 给 conflict 里的一个 agent 加一条 constraint。low level 用 space-time A* 给被加了 constraint 的那个 agent 重新规划。

CBS 为什么是 optimal 的？

三点。第一，分支不丢解：任何合法的 solution 一定满足两个子 node 之一的 constraint。第二，node 的 cost 是 lower bound：每个 agent 走的是满足 constraint 的最短路，还没处理的 conflict 被忽略了。第三，high level 按 cost 做 best-first，所以第一个没有 conflict 的 node 的 cost，不大于其他所有 node 的 lower bound。

CBS 什么时候会很慢？

conflict 多的时候。每个 conflict 让 tree 分一次叉，最坏情况是指数级。典型的坏情况是 one-wide corridor 里对头：其中一个必须等另一个完全通过，cost 要增加很多，而每条 constraint 只抬高一点 cost。corridor 每长一格，node 数大约翻一倍。

PP 和 CBS 怎么选？

看规模和时间预算。几十个 agent、需要质量保证，用 CBS。上百上千个 agent、每几秒 replan，用 PP 做主干。常见的组合是 PP 负责全局，PP 卡住的地方用 CBS 做局部修复。

想比 PP 质量好、又比 CBS 快，有什么办法？

两个方向。一是 bounded-suboptimal 的 CBS，比如 ECBS：允许 cost 最多是 optimal 的 w 倍，换来快几个数量级。二是 PBS：在 conflict 处搜索两个 agent 的 priority 谁高谁低，相当于自动找 PP 的顺序。

系统设计

lifelong MAPF 和 one-shot MAPF 有什么不同？

one-shot 里每个 agent 只有一个 goal，全部到达就结束，目标是 SoC 或 makespan。lifelong 里 agent 到达之后马上有新的 goal，永远不结束，目标是 throughput。做法是 rolling horizon：每隔 h 步用 one-shot 算法的 window 版本重新规划一次。

window w 和 replan 周期 h 怎么选？

必须 h ≤ w。w 小了短视，容易把 robot 带进堵点；w 大了规划慢，而且远处的 conflict 解了也白解。h 小了算力开销大；h 大了对新 task 和延误的反应慢。实际是在仿真里扫参数，看 throughput 和 planning time 的 p99。

这一轮规划超时了怎么办？

继续执行上一轮 path 剩下的部分。因为 w 大于 h，上一轮还有 w − h 步没有 conflict 的余量。同时可以缩小 window，或者只给一部分 robot 重新规划，保证下一轮能按时算完。

task assignment 怎么建模？greedy 有什么问题？

建一个 cost matrix，cij 是 robot i 做 task j 的代价，包括到 pickup 的距离、pickup 到 delivery 的距离、deadline 项和 congestion penalty。用 Hungarian algorithm 求 optimal 的一对一匹配，复杂度 O(n³)。greedy 每次选最小的一对，可能把最近的 robot 抢走，让别的 task 只能分给很远的 robot。

one-wide corridor 里两个 robot 对头，怎么办？

以预防为主：把 corridor 当成一个资源，同一时间只允许一个方向；出 corridor 的 robot 优先；出口有空位才允许进入；或者干脆规定成 one-way。兜底是在执行时维护 wait-for graph，发现环就让 priority 最低的 robot 退到最近的空位，然后局部 replan。

一个 robot 晚到了 2 秒，原来的 plan 还安全吗？

如果死守时刻表，就不安全。办法是执行时只保证先后顺序：plan 里 A 先过某个 cell、B 后过，那么 B 等 A 真的离开之后再进。这样任意延误下都不会撞。代价是延误会沿着依赖关系传播，超过阈值就 replan。

为什么让每个 robot 都走自己的最短路，往往是错的？

因为最短路会在同一个地方交汇，造成拥堵。全局更好的做法常常是让一部分 robot 绕路，或者先让开。PP 实验台里的“3 个 agent”就是例子：每个 agent 贪心地选最短路，SoC 是 9 或 10，协调之后是 7。

throughput 下降了，怎么判断问题出在哪一层？

分层看指标。空驶距离占比高，说明 assignment 有问题。wait 时间占比高、拥堵集中在某些 cell，说明 planning 或者地图的交通规则有问题。计划的时间和实际的时间偏差大，说明 execution 有问题。

1000 个 robot、每 5 秒 replan，你怎么设计？

分三层。assignment 层每个周期用 Hungarian algorithm 匹配空闲的 robot 和 task，cost 里带 deadline 和拥堵。planning 层用 rolling horizon，window 里跑 windowed PP，deadline 近的优先，按楼层分区并行；PP 卡住的地方用 CBS 局部修复；窄 aisle 用整段预约和出 corridor 优先来防 deadlock。execution 层只保证先后顺序，延误超过阈值就 replan。指标看 throughput、准时率、planning time 的 p99 和 deadlock 次数。
